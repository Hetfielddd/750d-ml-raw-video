# Read-only Thumb address-load candidates

`scripts/find_thumb_xrefs.py` searches a locally supplied 750D 1.1.0 ROM1 image for narrow Thumb instruction patterns that load addresses of selected strings. It does not execute firmware, contact a camera, change the input, identify function boundaries, or approve addresses for use on hardware.

```sh
python scripts/find_thumb_xrefs.py /private/path/ROM1.BIN
python scripts/find_thumb_xrefs.py /private/path/ROM1.BIN --marker lv_save_raw --limit 16
```

The CLI enforces the existing 32 MiB DIGIC 6 layout and requires the upstream 750D 1.1.0 additive signature. FIR containers, partial dumps, and signature mismatches are rejected. The sum is not cryptographic authentication: one test deliberately constructs an artificial matching image and verifies that authenticity remains false. No actual camera dump was analyzed in this work.

## Supported patterns

- Thumb LDR literal T1: low registers, positive PC-relative offset.
- Thumb LDR literal T2: R0-R12, positive or negative PC-relative offset.
- Immediately adjacent MOVW followed by MOVT into the same R0-R12 register, combining their immediate values into a 32-bit address.

Literal addresses use aligned PC plus four, with bounds checks before reading a word from the input segment. Both ROM execution aliases, 0xFC000000 and 0xFE000000, are considered independently. Addresses loaded from literal pools may use either alias. Candidate results contain instruction and literal file offsets, virtual addresses, register, encoding class, and loaded value. Per-target limits and truncation flags bound output.

Markers are exact NUL-terminated ASCII strings, unlike the earlier inspector's substring search. Supply the full string with `--marker` when a default marker is only a prefix of an actual message. Missing results do not prove that the event procedure or function is absent.

## Interpretation limits

The scanner tests every aligned halfword without code/data boundaries. A hit may be data, an unreachable instruction, or the second halfword of another instruction. Even a genuine address load does not establish the start of a function, calling convention, DMA channel, buffer lifetime, or safe execution context. It is a candidate for subsequent disassembly and cross-reference analysis.

The tool intentionally does not cover separated MOVW/MOVT pairs, intervening register writes, address arithmetic, relocated RAM code, indirect references, registration-table semantics, or complete control flow. Do not use its output directly as platform stubs. No guessed 750D hardware address is introduced.

## Verification

Six Python tests cover PC alignment, literal bounds, halfword alignment, capped hits, truncated wide instructions, address-space validation, FIR/partial-input rejection, and a full artificial ROM report with both aliases and signature mismatch rejection. Together with the existing tests, 15 Python tests pass.

The ARM test runner also assembles a Cortex-R4 Thumb fixture with GNU assembler and checks the actual generated bytes against four expected candidates: T1 LDR, positive T2 LDR, negative T2 LDR, and adjacent MOVW/MOVT. Wrong-register and separated pairs must be rejected. This is independent encoding evidence, not execution of real Canon firmware.

```sh
python -m unittest discover -s scripts -p 'test_*.py' -v
python scripts/test_raw14_arm.py --toolchain /path/to/arm-toolchain/bin --upstream-source /path/to/magiclantern
```

The existing five ARM component suites and 19 upstream layout assertions still pass. The new candidate check does not require a ROM or additional Python packages.
